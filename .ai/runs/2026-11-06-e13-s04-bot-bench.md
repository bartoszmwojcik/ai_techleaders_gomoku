## Spike T01 (#263) — udany

- Minimalna trasa z `new Worker(new URL("…/spike-worker.ts", import.meta.url), { resourceLimits: { maxOldGenerationSizeMb: 64, maxYoungGenerationSizeMb: 16 } })`; wątek importuje `chooseMove` z `@gomoku/core` (źródła TS).
- `next build` + `next start` lokalnie: działa, Turbopack emituje fragment `[worker thread]-…`.
- Obraz produkcyjny `docker build --build-arg LOW_MEMORY=1` (`node:22-slim`, Node 22.23.4), `docker run --cpus=1 --memory=2g --memory-swap=2g`: działa. Rozruch wątku 39–84 ms; poziom 2, TT 16 MB, głębokość 8, 11 kamieni: 530 ms, 71 tys. węzłów; sterta wątku ~10 MB; RSS procesu 142–166 MB, szczyt w czasie obliczenia +17…+34 MB.
- Sonda w kontenerze `--memory=2g`: `process.availableMemory()` = 1892 MB, `process.constrainedMemory()` = 2048 MB, `os.freemem()` = 2680 MB (pamięć maszyny wirtualnej Dockera, nie limit).
- Decyzja: wątek roboczy (R5) bez planu awaryjnego. Kod spike'a nie wszedł do repozytorium; wynik w specyfikacji (faza S04) i lekcji `2026-11-06-worker-threads-under-turbopack`.

## Pomiar T02 (#264) — lokalnie

Obraz produkcyjny zbudowany z gałęzi (`LOW_MEMORY=1`), `docker run --rm --cpus=1 --memory=2g --memory-swap=2g gomoku-app:latest npm run -s bot:bench -- …`. Maszyna: laptop 8 rdzeni / 16 GB, Docker Desktop (VM), w tle inne procesy (obciążenie hosta 8–11) — liczby są zaszumione.

Ocena wg R18:

- p95 ruchu ≤ 1,2 × cel (1800 ms): **spełnione** (1508 / 1514 ms). Ruchy kończy cel (flaga stopu po 1,5 s: 148/200 i 46/60) albo ukończone przeszukiwanie (52 i 14; m.in. wygrana/blok bez szukania).
- max ≤ pułap + 250 ms (3250 ms): **spełnione** (≤ 1518 ms; żaden ruch nie dotknął pułapu, 0 problemów w logu).
- p99 opóźnienia pętli zdarzeń głównego wątku ≤ 50 ms: **spełnione** (13,6 / 35,1 ms; `monitorEventLoopDelay` z rozdzielczością 10 ms, więc wartości zawierają ~10 ms próbkowania). Maksima 74–96 ms to pojedyncze zdarzenia (start wątku, GC).
- Przyrost RSS ≤ 100 MB przy TT 16 MB: **niespełnione o 3 MB w benchu (103,1 MB)**. Bench uruchamia wątek przez `tsx` (każdy wątek ładuje loader i esbuild), a w zbudowanej aplikacji ten sam wątek dawał +17…34 MB (spike). Wniosek: bench lokalny zawyża RSS; przed decyzją potrzebny pomiar RSS w zbudowanej aplikacji na hoście (np. `docker stats` aplikacji w czasie partii z botem). Progów nie zmieniano.
- Odczyt innej partii ≤ 2 × bez obliczeń: **niezmierzone**. Pierwsza próba ze stosem `compose.prod.yaml` (aplikacja + PostgreSQL, `--probe-url …/api/health`) skończyła się zabiciem maszyny wirtualnej Docker Desktop przez OOM hosta (10:31; host miał ~3 GB wolnego przy innych sesjach), zanim bench wypisał wynik. Powtórzono bez stosu (sam kontener, bez sondy HTTP). Test integracyjny `game-bot-worker.test.ts` sprawdza, że zbudowana aplikacja odpowiada w czasie ruchu poziomu 2 (p95 odpowiedzi < max(250 ms, połowa czasu ruchu)), a ten sam plik uruchamia `bot:bench` z progiem p99 pętli ≤ 50 ms.

Werdykt lokalny: **przybliżenie akceptuje czas i pętlę zdarzeń; RSS na granicy (artefakt `tsx`), odczyt innej partii niezmierzony.** Decyzja „akceptujemy / odrzucamy” (R18) i zmiana statusu A-21/A-22 czekają na pomiar na hoście docelowym — wymaga zgody właściciela (`docker exec` w kontenerze aplikacji na mikr.us, bez równoległego builda, z `--probe-url`).

Wnioski:
- Sonda `process.availableMemory()` w kontenerze na mikr.us (LXC) zwraca pamięć hosta, nie limit kontenera, więc „siła zależna od RAM” tam nie działa; ustawiono `BOT_FIXED_MEMORY_MB=1024` (tablica 16 MB, głębokość ≤ 8).
- Bot poziomu 2 na tym hoście liczy ok. 19 razy mniej węzłów na sekundę niż w kontenerze lokalnym i osiąga głębokość p50 3 (lokalnie p50 7), więc przewaga nad poziomem 1 jest tu mniejsza niż w teście R17 (który działa na limicie węzłów, nie czasu).
- Pomiar zawyża opóźnienie pętli (start wątku przez `tsx`, równoległy ruch produkcyjny); nie zmierzono go w zbudowanej aplikacji.

**Decyzja właściciela (2026-11-06):** „B, włącz z `BOT_FIXED_MEMORY_MB=1024`” — włączenie bota mimo jednego niezaliczonego progu (wyjątek od R18). Wdrożone tego samego dnia: `BOT_ENABLED=true`, `BOT_FIXED_MEMORY_MB=1024` w `.env.production`.
